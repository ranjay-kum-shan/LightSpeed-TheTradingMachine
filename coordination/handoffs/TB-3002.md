## Completion Summary

`src/trading_bot/data/models.py` now holds the canonical market-data values:
`Instrument`, `DailyBar`, `CorporateAction`, and `DatasetManifest`, plus the
`DatasetType`, `ValidationResult`, and `CorporateActionType` enums and the pinned
`CANONICAL_SCHEMA_VERSION`. Field names, types, and optionality follow the
[canonical schema tables](../../docs/04-data-specification.md) exactly.

Every timestamp field is normalized through the TB-1004 `ensure_utc` primitive,
so a naive value cannot enter a canonical row and `session_date`, `ex_date`,
`record_date`, `pay_date`, `effective_start`, and `effective_end` stay
exchange-local dates. A `DailyBar` may not claim `available_at_utc` earlier than
its own `bar_close_utc`, which makes lookahead availability unrepresentable.
Corporate actions must be complete for their own type: a split carries a positive
ratio, a cash dividend carries an amount with exactly one matching currency, and
a symbol change carries two different symbols. The manifest requires sorted and
duplicate-free lineage, lowercase SHA-256 digest shapes, a non-negative row
count, a coherent effective range, no self-parentage, and a canonical sorted
request parameter list that refuses secret-like keys.

The most consequential design choice is what these types deliberately do *not*
enforce. See the boundary note in Contracts and Requirements.

**Rule boundary, audited and enumerated.** The dataset lifecycle places
`NORMALIZED` before `VALIDATING`, and `DV-001`, `DV-002`, `DV-004`, and `DV-005`
must each report *offending canonical rows*. If a canonical row refused to hold
a crossed high and low, a negative volume, or a duplicate key, TB-3005 could not
detect, report, or quarantine those datasets. Cycle two audited the claim that
only two kinds of rule are enforced and disproved it, so the module docstring and
this section now enumerate four classes:

1. Representational rules, without which the value has no defined meaning: aware
   UTC timestamps, finite `float` and `Decimal` values, `int64`-representable
   integers that are not `bool`, non-empty trimmed identity strings, ISO 4217
   currency shape, SHA-256 shape for `content_hash`, sorted and duplicate-free
   lineage lists, and a non-degenerate `bar_open_utc` to `bar_close_utc`
   interval. Enum membership is a static type rule only; nothing checks it at
   runtime.
2. One availability safety rule: `available_at_utc` may not precede
   `bar_close_utc`. No `DV-*` rule covers availability ordering, so no downstream
   check would catch lookahead, and unlike a crossed high and low a lookahead row
   can never be reviewed into acceptance.
3. Corporate-action completeness rules: a split carries a positive ratio, a cash
   dividend carries a non-negative amount, a cash amount carries exactly one
   currency, and a symbol change carries two different symbols. Without these an
   action cannot be applied at all.
4. One security policy rule: manifest request parameters refuse secret-like key
   names, because a lineage record is immutable and a key written once cannot be
   withdrawn.

Coverage bounds, lineage-graph integrity, duplicates, gaps, and price or volume
plausibility are deliberately absent. Two rules that fell outside this
enumeration - `effective_end` versus `retrieved_at_utc` and self-parentage - were
removed in cycle two rather than reclassified.
`test_bar_leaves_validation_rule_violations_representable` and
`test_manifest_leaves_lineage_rule_violations_representable` pin the boundary so
a later change cannot silently break TB-3005.

Decision, migration, schema, or compatibility impact: additive only.
`CANONICAL_SCHEMA_VERSION` is introduced at `"1"`. `DOMAIN_CONTRACT_VERSION` is
untouched because no domain contract changed.

Residual safety or security risk: the manifest secret-key guard inspects key
names only. After two review cycles it refuses six exact names and seventeen
fragments, covering `api_key`, `api_token`, `auth_token`, `bearer_token`,
`access_token`, `security_token`, `personal_access_token`, `request_signature`,
`client_secret`, `subscription_key`, `session_key`, `consumer_key`, `app_key`,
`shared_key`, `passphrase`, `pwd`, `sig`, `auth`, `jwt`, and `key`, while an
explicit allowlist keeps the legitimate `page_token`, `next_page_token`, and
`continuation_token` pagination cursors. It still cannot detect a secret carried
inside a *value*, so a query string such as `https://host/v2/bars?apikey=REAL`
stored under the key `url` would be written into an immutable lineage record.
That is a real exposure, not a theoretical one, and it is deferred to TB-1005
rather than solved here. A name-based guard is also inherently incomplete: any
unusual key name passes. No provider name, endpoint, credential, or network path
is introduced by this task; the example provider strings appear only in test
fixtures.
