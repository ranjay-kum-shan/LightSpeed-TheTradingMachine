## Objective

Persist capital-flow-aware daily loss, drawdown, and sticky halt outcomes so a
process restart, improving intraday mark, or new session cannot silently remove
risk denial.

## Contracts and Requirements

| Contract | Relevant section or invariant | Required behavior |
| --- | --- | --- |
| [Risk Specification](../../docs/03-risk-and-safety.md) Loss and Drawdown Semantics | Daily PnL excludes documented deposits and withdrawals; high-water equity advances only under the approved mark policy | Signed capital flows are idempotent, daily loss is flow-adjusted, and drawdown uses a flow-adjusted durable reference |
| [Risk Specification](../../docs/03-risk-and-safety.md) Trading State Machine | Daily loss is sticky through the session; drawdown is sticky across restart and session boundaries | A better mark cannot clear either halt; a new session may clear only the prior daily-loss halt |
| [Risk Specification](../../docs/03-risk-and-safety.md) Restart Policy | Restart rebuilds risk counters, session equity, and high-water equity from durable facts | Closing and reopening the store returns the same halt, values, reason, and revision |
| [Requirements](../../docs/01-requirements.md) RISK-004 | Internal halt paths must be available and tested | Daily loss produces `LOSS_HALTED`; drawdown produces `HARD_HALTED` with stable reasons |
| [Requirements](../../docs/01-requirements.md) NFR-SAFE-001 | Missing, ambiguous, or broken state fails closed | Missing state, conflicting capital-flow identity, stale marks, and database failures raise instead of synthesizing a clear state |
| [Architecture](../../docs/02-architecture.md) State Ownership | Risk counters derive from broker facts and durable event state | The store records one authoritative state per scope and preserves mutation evidence transactionally |
| [Storage Foundation](../handoffs/TB-1006.md) | SQLite migrations and restricted transaction boundary are integrated | TB-2003 uses the delivered API without exposing a raw connection or creating runtime data in the repository |

Conflicting or missing contract: an authenticated owner-reset mechanism and
approval registry do not exist. This task therefore exposes no API that clears a
hard drawdown halt. That conservative omission preserves the higher-level safety
contract and remains explicit in the handoff.

## Scope

### In Scope

- Immutable durable risk-state values with canonical UTC timestamps and finite,
  positive equity validation.
- One task-owned SQLite migration for current risk state, capital-flow identity,
  and append-only state-transition evidence.
- Initialization, current-state loading, idempotent capital-flow recording,
  equity-mark assessment, reconciled session close, and next-session start.
- Signed external-flow adjustment for daily PnL and the high-water reference so
  deposits and withdrawals do not manufacture profit or drawdown.
- Sticky daily-loss and hard-drawdown transitions with drawdown taking
  precedence when both limits cross.
- Integration of flow-adjusted daily loss into the existing pure risk engine.
- Focused restart, session-boundary, capital-flow, threshold, stale-input,
  conflict, rollback, and migration tests.

- Live trading, leverage, shorting, credentials, or real account data.

## Decisions and Assumptions

| Item | Type | Evidence | Resolution or escalation |
| --- | --- | --- | --- |
| Positive capital flow means deposit; negative means withdrawal | Decision | Daily PnL must neutralize both directions | Compute daily PnL as current equity minus session-start equity minus net signed flow |
| Capital flows adjust the high-water reference by the same signed amount | Decision | A deposit must not appear as profit and a withdrawal must not manufacture drawdown | Require a reconciled current equity with each flow and adjust the durable reference atomically |
| Halt outcome is persisted, not recalculated only at load | Decision | New limits or an improving mark after restart must not clear prior denial | Store halt state and reason in the current row and append transition evidence |
| A new session clears only a daily-loss halt | Decision | Specification permits daily reset at a session boundary but requires hard halt owner review | Preserve `HARD_HALTED`; expose no hard reset API |
| High-water advancement requires reconciled session-close identity | Decision | High water updates only under an approved mark policy | Require a non-empty reconciliation ID and record it with the close transition |
| SQLite decimal values use canonical strings | Assumption | SQLite has no exact decimal storage class | Serialize finite Decimal values with fixed-point text and validate every loaded row |
| Equivalent Decimal scales share one canonical text | Decision | Flow identity must treat `1000`, `1000.0`, and `1E+3` as the same exact value | Strip only insignificant fixed-point zeros; do not use context rounding |
| Every risk event forms a SHA-256 chain | Decision | Count and latest-row checks did not detect earlier-event mutation | Verify every revision, predecessor hash, event hash, and current/latest equality on load |
| Flow ledger and event history must agree exactly | Decision | A deleted or altered flow row would otherwise leave restart evidence ambiguous | Compare counts and all identity, session, value, reconciliation, and time fields in both directions |
| Between-session flows are explicit | Decision | An arbitrary new session equity could conceal a deposit, withdrawal, or market gap | Optional signed opening flow adjusts high water; unexplained gaps remain subject to drawdown |
| Effective risk profile identity is durable | Decision | Reopening with looser limits must not reinterpret existing state silently | Require a 64-character profile hash, persist it atomically per scope, and reject mismatches |
| Risk snapshots require durable flow and halt facts | Decision | Defaults or manual mapping could bypass daily loss or sticky halt | Remove the flow default; require halt state/reason; overlay through `RiskState.enforce_snapshot`; engine also denies directly from durable fields |

Do not turn an implementation assumption into a project decision without the
decision-record process.
